 Formato de UUID de las caracteristicas:

       0xN, 0xC0,0xF1,0xA1,0x12,0x12,0xEF,0xDE,0x15,0x23,0x78,0x5F,0xEA,0xBC,0x00,0x00
   O sea: para una caracteristica nueva "c007" -> primer byte 0x07, lo demas igual.

 Todos los enteros van LITTLE-ENDIAN, structs sin relleno (os_mbuf_append tal cual).

3) COMO FUNCIONA UN "EVENTO" HOY (ejemplo: boton de captura)  --- patron a copiar
-------------------------------------------------------------------------------
 El patron que FUNCIONA para mandar un evento consola->app es:

   a) El evento se detecta en su tarea (ej. vTaskJoystickControl, flanco de boton).
   b) Esa tarea NO llama a ble_gatts_notify_custom directo. Solo:
        - actualiza la variable espejo (ej. appCaptureEvt++)
        - marca un flag  (ej. s_capture_notify_pending = true)
   c) vTaskNimbleNotify (la tarea que ya notifica tilt/batt/temp/enc) ve el flag
      cada 100 ms, manda el notify con ble_gatts_notify_custom, y limpia el flag
      solo si el notify salio OK (rc == 0).
   d) El payload es un valor ABSOLUTO (contador), no un "1". Asi, si se pierde un
      notify (BLE notify no tiene ACK), el siguiente igual trae el total al dia.

 IMPORTANTE: notificar desde otra tarea que no sea vTaskNimbleNotify daba
 problemas (llegaba solo el primer notify). SIEMPRE notificar desde
 vTaskNimbleNotify via flag/cola.

 La suscripcion del cliente se registra en gattSvrSubscribeCb: ahi se guarda
 conn_handle y cur_notify en la struct notify_state_t correspondiente.

 -------- OPCION B: canal generico de eventos (hacer 1 vez, despues escala) ----

 Idea: UNA caracteristica c007 "EVENT" (Read+Notify) que lleva un frame con id +
 valor, igual que el HMI hace {reg, value}. Agregar un evento nuevo = un id nuevo
 en un enum + una llamada. NO se toca la tabla GATT ni hay re-discovery.

 Caracteristica c007 "EVENT"  (Read + Notify)
   Payload = 6 bytes LE:
       evt_id : u8    -> que evento (enum ble_evt_id_t)
       seq    : u8    -> +1 por evento (wrap 255); la app detecta si perdio alguno
       value  : i32   -> dato del evento

 (Opcional, mismo momento) c008 "COMMAND"  (Write)  IRIS -> consola
   Payload = 6 bytes LE:  cmd_id:u8, rsv:u8, value:i32
   En el access_cb de c008, caso BLE_GATT_ACCESS_OP_WRITE_CHR: parsear y
   switch(cmd_id) { ... }   <- igual que hmi_handle_reg().

 Tabla de eventos (enum ble_evt_id_t en main.c, documentar aca):

   evt_id | nombre              | value
   -------+---------------------+------------------------------------------------
   0x01   | BLE_EVT_CAPTURE     | contador de pulsaciones del boton de captura
   0x02   | (libre)             |
   0x03   | (libre)             |
   ...    |                     |

 Tabla de comandos (enum ble_cmd_id_t en main.c), si se agrega c008:

   cmd_id | nombre              | value
   -------+---------------------+------------------------------------------------
   0x01   | (libre)             |
   ...    |                     |

 Firmware para B:
   - helper  ble_evt_send(uint8_t evt_id, int32_t value)
       -> arma el frame, seq++, lo mete en una cola FreeRTOS (como xQueueHmiTx).
   - vTaskNimbleNotify saca de la cola y hace ble_gatts_notify_custom sobre c007.
   - Agregar un evento nuevo desde cualquier tarea:  ble_evt_send(BLE_EVT_XXX, v);

 Despues de B, "mandar algo nuevo a IRIS" = agregar un evt_id a la tabla de
 arriba + llamar ble_evt_send(...). Nada mas.


5) REGLAS Y GOTCHAS
-------------------------------------------------------------------------------
 - Notificar SIEMPRE desde vTaskNimbleNotify (via flag o cola). No desde la
   tarea que genera el evento (llegaba solo el primer notify).

 - BLE notify NO tiene ACK: puede perderse. Por eso mandar valor absoluto
   (contador), no pulsos "1". La app lee la caracteristica al conectar (base) y
   trabaja con el delta. Si un evento es critico y no se puede perder, usar
   INDICATE (BLE_GATT_CHR_F_INDICATE) en vez de NOTIFY: tiene ACK, pero es mas
   lento y solo 1 pendiente a la vez.

 - Al agregar/quitar caracteristicas cambia la tabla GATT -> los clientes con
   cache GATT (Windows/BlueZ, moviles ya emparejados) tienen que re-descubrir o
   se les limpia el cache / se re-emparejan. Con la OPCION B esto NO pasa: la
   tabla no cambia.

 - Subir BLE_PROTO_VERSION (#define en main.c) cada vez que se agrega un evt_id,
   cmd_id o caracteristica. La app lee c006 al conectar para saber que soporta.

 - Subir tambien la version del proyecto en CMakeLists.txt (project ... VERSION).

 - Espejar SIEMPRE el cambio en tools/ble_monitor.py (CHAR_DEFS + decode_payload)
   para poder probar sin depender de IRIS.

 - La suscripcion (CCCD) del cliente se registra en gattSvrSubscribeCb. Si un
   notify "no llega", revisar por serie las lineas "SUBSCRIBE: ..." y comparar
   attr_handle con el *ChrValHandle correspondiente.
